# Open Music Player — учебный план по Nuxt 4

Источник правды по курсу. Текущий этап, статусы и решения живут в [`PROGRESS.md`](./PROGRESS.md).

## Зачем этот файл

Нейронка не помнит прошлый чат. Если план и прогресс лежат в репозитории, любой новый диалог может продолжить обучение с того же места, а не изобретать курс заново.

Три якоря контекста:

| Файл | Роль |
| --- | --- |
| `AGENTS.md` | Вход для любого агента (Cursor, Cline, Codex). Режимы Mentor / Implementer |
| `docs/LEARNING.md` | Чему учимся и в каком порядке |
| `docs/PROGRESS.md` | Где мы сейчас, что уже сделано, что решили |
| `.cursor/rules/nuxt-mentor.mdc` | Как ментор обязан себя вести в учебном чате |

Память и проверки агента: `.agent/`. Ученик туда не ходит.

## Профиль и цель

Ты — junior Vue-разработчик. Цель курса — не выучить перечень API Nuxt, а научиться смотреть на приложение и объяснять:

> что происходит, где выполняется код, как устроено состояние, как данные проходят через систему и почему архитектура выглядит именно так.

Стек на старте (уже в репозитории):

- Nuxt `^4.5.2`
- Vue `^3.5.42`
- TypeScript из коробки
- структура Nuxt 4 с каталогом `app/`

Источник музыки — внешний open/free API. Выбираем и проверяем его на этапе 4, не раньше: до этого нам не нужен ключ, CORS и формат ответа.

## Как учимся

Не формат «вот 20 composables, запомни». Код пишет ученик. С **2026-09-24** цикл сессии такой (уточнение ученика, важнее более ранней схемы с отдельным экзаменом в начале):

```text
подробная теория + крошечный пример (без правок проекта)
    ↓
ученик своими словами говорит, что понял
    ↓
ментор поправляет неточности — задачи ещё нет
    ↓
что сделать в проекте на этом срезе, зачем, definition of done
    ↓
ученик говорит, какие файлы и API возьмёт и почему; ментор проверяет план
    ↓
ученик реализует сам, ментор ревьюит по ходу
    ↓
когда срез готов — контрольные вопросы этапа
    ↓
этап закрыт → пометки в PROGRESS.md → следующий этап
```

Короткий мост с прошлого этапа — часть теории, не отдельный зачёт.

### Роли

- **Ты** пересказываешь теорию, предлагаешь план файлов, пишешь код, отвечаешь на контрольные своими словами.
- **Ментор** объясняет теорию, ловит неточности до задачи, ревьюит параллельно с реализацией, закрывает этап вопросами. Код за тебя не пишет, пока ты явно не попросишь после самостоятельной попытки.
- Заметки в `docs/` и `.cursor/` ведёт ментор. Ученик туда не заглядывает, чтобы продолжать курс.

Если забыл, как объявить props — это нормально. Ментор сначала напоминает синтаксис на крошечном примере, потом ты применяешь его в задаче.

### Формат сессии

1. Ментор читает этот файл и `PROGRESS.md`.
2. Теория текущего механизма — подробно, понятным языком.
3. Пересказ ученика → правки, пока формулировка не точная.
4. Формулировка задачи в проекте. Стоп: код ещё не пишем.
5. План ученика (файлы, API, почему) → оценка.
6. Реализация ученика, ревью по ходу.
7. Контрольные вопросы и обновление `PROGRESS.md`. Этап закрыт — только после этого следующий.

Одна сессия = один вертикальный срез этапа, не обязательно весь этап. Этап закрываем только когда выполнен definition of done и ты ответил на контрольные.

### Что не делаем

- Не скипаем фундамент ради «сразу плеер».
- Не тащим Pinia / Nitro / Tailwind / auth, пока задача этого не требует.
- Не учим устаревшее: `process.client` / `process.server` заменяем на `import.meta.client` / `import.meta.server`.
- Не кладём Vue-код в корень «как в Nuxt 3». В Nuxt 4 приложение живёт в `app/`.
- Не откладываем TypeScript «на этап 11». Типизируем сразу; этап 11 — это граница с внешним API, а не введение в типы.
- Не делаем «красивый UI» вместо архитектуры, но и не оставляем страницы нечитаемыми: с этапа 1 есть минимальный каркас, полировка — этап 14.

## Этап 5. SSR и hydration

### Зачем сейчас

Это один из ключевых этапов. Не «Nuxt умеет SSR», а наблюдение за жизненным циклом на нашем приложении.

```text
Запрос
  → Nitro
  → Vue render на сервере
  → HTML + payload
  → Браузер
  → Hydration
  → Интерактивное Vue-приложение
```

### Что изучаем

- server lifecycle vs client lifecycle
- почему на сервере нет `onMounted`
- payload и повторное использование данных при hydration
- `import.meta.client` / `import.meta.server`
- почему `localStorage`, `window`, `document` нельзя читать в setup без охраны
- hydration mismatch

### Эксперимент

Намеренно читаем `localStorage` в setup страницы, смотрим ошибку, чиним правильно. Это важнее абзаца в документации.

### Definition of done

- [x] Эксперимент с `localStorage` проведён и разобран
- [x] Ты словами проговариваешь путь одного запроса `/track/123` от URL до гидрации
- [x] Нет случайных обращений к browser API на сервере

### Checkpoint

1. Какие Vue-хуки не выполняются на сервере и почему?
2. Почему HTML с сервера и дерево Vue в браузере должны совпасть?
3. Чем `import.meta.client` лучше комментария «это только для браузера»?

## Этап 12. Middleware и plugins

### Зачем сейчас

Механизмы подключаем только когда появилась задача, а не «потому что в курсе такая тема».

### Middleware

Когда появится пользовательская зона (`/profile`, приватные плейлисты) — защищаем её route middleware.

До auth (этап 17) middleware можно показать на учебной задаче, которая уже реальна: например, редирект с пустого `/search` или валидация param. Искусственный `if (!loggedIn)` без пользователя не делаем.

### Plugins

Клиентский plugin — для инфраструктуры, которой правда нужно жить всю сессию приложения (инициализация audio/player), а не для «положить store в plugin потому что можно».

### Что изучаем

- route / global / named middleware
- plugins, `.client` / `.server`
- порядок выполнения в lifecycle

### Definition of done

- [ ] Есть хотя бы один middleware и один plugin с понятной причиной
- [ ] Ты объяснил, почему это не composable и не server middleware

### Checkpoint

1. Когда plugin, когда composable, когда server middleware?
2. Почему app middleware бежит и на сервере, и на клиенте?
3. Что сломается, если инициализировать `Audio` в plugin без `.client`?

## Что усилено относительно исходного плана

Исходная последовательность **сохранена**: фундамент → усложнение продукта → механизм Nuxt под реальную задачу. Короче курс не делаем.

Изменения для обучения, а не для скорости фич:

1. **Контекст между чатами** зафиксирован файлами, а не памятью модели.
2. **Этап 1** стартует с уже созданного Nuxt 4.5, а не с пустой папки.
3. **Vue-этап** — диагностика junior Vue, не второй курс фреймворка.
4. **Минимальный UI с этапа 1**, визуальный polish — этап 14. Иначе ты учишь архитектуру на нечитаемых страницах и бросаешь мотивацию.
5. **TypeScript с первого кода**. Этап 11 сужен до DTO-границы и `shared/`.
6. **Выбор API** — отдельный шаг 4.0 с записью решения.
7. **CORS** используем как мост к Nitro, а не как случайный блокер.
8. **Этап 9** — ретроспектива архитектуры, потому что composables появятся раньше.
9. **Nuxt 4-актуальность:** `app/`, `shared/`, `import.meta.client`, shared keys у `useFetch`.
10. **Checkpoint + definition of done** на каждом этапе, иначе легко «вроде прошли».
11. **Повторение в начале сессии**, чтобы знание не выветривалось к этапу 10.
